Description list

A description list pairs a label with a value for one record. It is how a booking summary reads: artist, date, gathering, church, fee, deposit.

WCAG 2.2 AAStatus: stableNative <dl>Class .dl

Overview

Use a description list for the facts of a single record: the booking Naomi is about to send, the request an artist is reading, the receipt after a deposit. Each pair is a term (<dt>) and its value (<dd>).

  • Vertical (.dl) stacks the label over the value. Use it in narrow places: the booking stub, a card, a dialog.
  • Horizontal (.dl--horizontal) puts labels in a column on the left with a rule under each row. Use it for a full summary or receipt.
  • Stub (.dl--stub) sets values in the mono ticket-stub face, uppercase. Use it on the booking stub and receipts, where the summary should read like a printed ticket.
  • Use a table to compare several records, and a list when items have no labels.

Anatomy

  1. Term<dt>: mono overline, 12px, uppercase, stamp tracking, muted.
  2. Value<dd>: body text, 16px, full strength. In .dl--stub, mono 14px uppercase.
  3. GroupA <div> around each pair; it carries the layout and the row rule.
  4. Row rule (horizontal)Hairline in --color-border-default under each pair, 12px above and below.

Definition grid (record details)

.definition is the description list of the booking and request pages and most dialogs: each pair is a .definition__row with the term as a muted, uppercase overline over the value, 16px between rows. .definition--two puts the rows in two columns from 576px; each row keeps its term and value together at the top of the cell. Use it for the facts of one booking (date, start time, gathering, church, artist, price) where the vertical .dl would run too long.

Receipt (money)

.receipt is the stub-face list for money: every row is a .receipt__row with the label left, the amount right in tabular figures and a dashed hairline under it. The last row, .receipt__total, is set in the display face between two thick rules. Fine print under the list goes in .receipt__fine (sentence case, caption size). Amounts follow L2-110: “$650”, “$162.50”. The server-error page reuses it for the reference and time a person quotes to support.

Sizes

Description lists have one size. Use the stub variant for a smaller, mono value.

States

A description list is not interactive, so it has no hover or focus. It has content states: loading, a value that is not known yet, and a value that just changed.

  • The horizontal variant has the same states; it is left out of the matrix only for width.
  • Loading keeps the real terms and puts a .skeleton where each value goes, so the layout does not jump.
  • Not set says when the value will exist, in muted text. Never leave a <dd> empty or write “N/A”.
  • Changed marks a value the person just edited, or one the artist changed, with the yellow .mark highlighter until the summary is confirmed. Say what changed in text too (“Abigail moved this to Sun 15 Nov”).

Responsive behaviour

  • The vertical list works at every width; values wrap under their term.
  • The horizontal list keeps two columns down to 360px: the term column is at least 8rem (128px) and takes a third of the width; the value takes the rest and wraps. Keep terms to two words so they do not wrap.
  • In the booking stub, which is narrow on desktop (the sidebar) and full width on phones, always use the vertical stub variant.
  • For a long summary on wide screens, two vertical lists side by side read better than one long horizontal list; place them in a .form__row or .grid.
  • .definition--two is one column below 576px and two from 576px (--layout-breakpoint-sm); rows align to the top so a long church name doesn’t push its neighbour down.
  • .receipt rows keep label and amount on one line; a long label wraps while the amount stays right-aligned.

Theming

The description list has no component tokens. Terms read --color-fg-muted in --text-overline; values read --color-fg-default in --text-body (or --text-stub for the stub variant); horizontal rows are ruled with --color-border-default. On the dark stage the same tokens resolve to paper on charcoal; nothing else changes. Inside the booking stub it follows the stub’s surface (--color-bg-surface), so it turns charcoal with the stub in the dark theme.

Accessibility

Role and pattern

A native <dl>. Each <dt>/<dd> pair is wrapped in a <div>, which HTML allows as the only wrapper. There is no APG pattern: screen readers announce a description list and, in most cases, the number of terms. Never fake one with a two-column table or with bold <span>s.

Keyboard

KeyAction
TabSkips the list; only links or buttons inside a value (for example “Change date”) receive focus.
Screen reader list keysMove by list and by item, reading each term and value together.

Focus

The list itself never takes focus. If a value has an edit link, put it at the end of that <dd> and name it with the term: “Change date”.

Labelling

Introduce the list with a heading (“Your booking”), and put both in a <section aria-labelledby> when the summary is a region of its own. Don’t put aria-label on the <dl> itself: it has no role that takes a name. Terms are the labels, so they must be visible text, not icons. When a value is loading, give its skeleton role="img" and aria-label="Loading", and set aria-busy="true" on the list. A changed value is announced through the page’s status region, not by the highlighter alone.

Terms are 12px, so they need the full 4.5:1; the muted token clears it on every surface. Row rules are decorative.

Motion

None. Loading skeletons stop shimmering under prefers-reduced-motion.

Touch

Nothing to tap unless a value holds a link; such links follow the 24px minimum and sit at least 8px from the next one.

Content

  • Terms are one or two nouns in sentence case: “Artist”, “Date”, “Gathering”, “Church”, “Fee”, “Deposit 25%”. CSS uppercases them.
  • Put the rule in the term when it explains the value: “Deposit 25%” then “$162.50”.
  • Values are complete: “Sat 14 Nov 2026”, “Riverside Community Church, Burlington”, “$650”. Add the year in summaries and receipts.
  • Order the pairs the way people check a booking: who, when, what, where, how much.
  • A value that does not exist yet says when it will: “When Abigail accepts”.

Sources

The mocks use two description lists, .definition and .receipt; the plain .dl variants above are not in the mocks yet and stay ready for compact summaries.

  • pages/booking-detail/default and every booking status (accepted, confirmed, cancelled…): “The request” as .definition--two, the payment aside as .receipt
  • pages/request-detail/default and its states: the same request facts for the artist, with .receipt__fine (“You’ll be paid $598 after the event.”)
  • pages/book/default and success: the booking summary before and after sending
  • Dialogs: dialogs/accept-request/default, dialogs/cancel-booking/default, dialogs/pay-deposit/default, dialogs/withdraw-request/default (what is about to change and the money)
  • pages/server-error/default: a .receipt with the error reference and time
  • pages/apply/success: the application summary

Drift fixed during extraction:

  • The stub heading used style="font: var(--text-h3)". It is now .stub__title, used in the stub example above.
  • Several display-font shorthands were inline (var(--font-weight-regular) var(--font-size-2xl) / 1 var(--font-family-display)). Prices and figures now use the role tokens --text-figure and --text-figure-lg.
  • Rows in .definition--two stretched to the tallest neighbour, separating short terms from their values; rows now align to the top. The two-column break follows the L2 SM breakpoint (576px).
