Component · Inputs

Form field

Every input on Zamaro sits in a field: a stamped label above, the control, then one line of help, an error or a counter below. The field does the wiring, so each control only has to be a control.

Overview

Use .field around every text field, textarea, select and date picker. Checkbox, radio and switch groups use a <fieldset> instead; see Checkbox.

  • Label (.field__label) is always visible and above the control. Placeholders are never labels.
  • Optional marker (.field__optional). Most booking fields are required, so Zamaro marks the exceptions: “Message (optional)”.
  • Help (.field__help) is one muted line under the control: a format, a limit or why we ask.
  • Error (.field__error) replaces nothing; it appears under the control, above the help, with a warning icon.
  • Success uses an inline message (.inline-msg--success) as help: “Abigail is free Sat 14 Nov”.
  • Counter (.field__counter) sits on the label row for fields with a limit.

Use <div class="field"> with <label for> whenever the field has help, an error or a counter. A wrapping <label class="field"> is fine for a bare label and control, as in the booking bar, but anything inside the label becomes part of the control’s name.

Anatomy

  1. LabelMono overline, 12px, uppercase, stamp tracking, in body ink. Names the control.
  2. Optional markerCaption size, sentence case, muted. Part of the label, so it is part of the name.
  3. CounterMono overline with tabular figures, on the label row (.field__row). Turns danger red and bold over the limit.
  4. ControlAny input, select or textarea. It owns its own height, border and focus ring.
  5. ErrorBold caption in danger red with a 16px warning icon. Says what is wrong and how to fix it.
  6. HelpCaption in muted ink. One sentence. Parts sit 4px apart (--space-1).

Variants

Add only the parts a field needs. Most booking fields are a label and a control.

Inline field

.field--inline keeps a field at least 12rem wide when it sits in a heading row, like the lineup’s sort.

  <select class="select" id="ff-sort"><option selected>Closest first</option><option>Highest rated</option><option>Price, low to high</option></select>
</div>

The wrapper has one size. The control inside sets the height; see Text field and Select sizes.

  • Invalid adds the error under the control. Keep the help if it still helps; put the error first.
  • Success swaps the help for a green inline message with a tick. Use it only for checks the booker cares about, like availability.
  • Read-only and disabled come from the control. The label stays in body ink so the value can still be read and understood.

Responsive behaviour

  • A field fills its column. Width comes from the layout (Form layout), never from the field.
  • Labels, help and errors wrap; nothing truncates. The error icon stays aligned with the first line.
  • The label row (.field__row) keeps the counter on the right; if the label is long, the label wraps and the counter stays put.
  • .field--inline sets a 12rem minimum so a field in a heading row does not collapse at 360px.

Theming

The wrapper reads semantic tokens: --color-fg-default for the label, --color-fg-muted for help, the optional marker and the counter, --color-danger-fg for errors and the over-limit counter, and --color-success-fg through .inline-msg--success. The controls inside carry the component tokens --field-bg, --field-fg, --field-border and --field-height; override those to re-skin inputs on a surface, never the field parts.

In dark mode the label turns paper, help a warm grey, errors a light red and success a light green, each at 4.5:1 or better on the dark surfaces.

Accessibility

Role and pattern

Native <label for> and aria-describedby, as in the W3C WAI forms tutorial. There is no APG widget pattern for a field; the control inside follows its own.

Keyboard

KeyAction
Tab / Shift+TabMoves to and from the control. Labels, help and errors are not focusable.
Click or tap the labelFocuses the control (a larger target for free).

Focus

Only the control takes focus. Its ring is the double ring (--shadow-focus): yellow inner, ink outer on paper; ink inner, yellow outer in dark mode. After a failed submit, focus goes to the error summary, whose links move focus to each invalid control.

Labelling

  • Every control has a visible <label>. The optional marker is inside it, so it is read: “Phone (optional)”.
  • aria-describedby lists the error first, then help, then the counter, so the reason is read before the hint.
  • An invalid control gets aria-invalid="true". Remove it, and the error element, as soon as the value is fixed.
  • Do not put help or errors inside a wrapping label: they become part of the control’s name and are read twice.
  • Counters are described, not live. When fewer than 20 characters remain, announce the remaining count once through a polite live region.
  • Fill autocomplete for known data (organization, tel, address-level2), per WCAG 1.3.5.

Errors and success never rely on colour: errors have a warning icon and bold text, success a tick, and the invalid control has a thicker left stripe.

Motion

Errors and help appear without animation. Do not slide them in; the layout shift is enough of a cue, and it should be small.

Touch

The label is part of the target. Controls are 44px tall by default. Keep 20px (--space-5) between fields so a thumb does not land in the wrong one.

Content

  • Labels are short nouns in sentence case: “Event date”, “Kind of gathering”, “Church”. A question is fine when it reads more naturally: “How far can they drive?”
  • Mark optional fields, not required ones: “(optional)”. No asterisks.
  • Help is one sentence that says why or how: “Only shared with an artist after they accept.”
  • Errors say what is wrong and what to do, without blame: “Abigail is booked Sun 15 Nov. Pick Sat 14 or Fri 20 Nov.” Not “Invalid date”.
  • Success names the good news: “Abigail is free Sat 14 Nov”. No typed “✓”; the icon does that.
  • Counters show “used / limit”: “112 / 500”.
