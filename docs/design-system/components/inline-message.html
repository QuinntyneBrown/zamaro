Inline message

A short line of status right where the booker is looking: under the date they picked, beside the button they pressed. It says one thing, with an icon and a colour that agree.

WCAG 2.2 AAStatus: stableLinked by aria-describedbyClass .inline-msg

Overview

Use an inline message for status that belongs to one control or one row: whether the artist is free on the date in the booking stub, why a field is invalid, that a change was saved. It sits directly under or beside its subject and is linked to it with aria-describedby.

  • Hint (no modifier, muted) gives advice before anything goes wrong: “Most churches book 4–6 weeks ahead.”
  • Info adds a fact the booker needs: “Travel is included within 120 km.”
  • Success confirms a check passed: “Abigail is free Sat 14 Nov.”
  • Warning means it will work, with a catch: “Another church asked for this date first.”
  • Danger means it won’t work as entered and says how to fix it. Inside a form field the error slot is .field__error, which looks the same as .inline-msg--danger; use .inline-msg--danger for errors outside a field, such as under a ticket stub.

When the message needs a title, an action or more than one sentence, use an alert. When it confirms an action that has no on-screen subject (saving an artist from a list), use a toast.

Anatomy

  1. Icon16px, aria-hidden, nudged 2px down to sit on the first line. Check for success, warning triangle for warning and danger, info circle for info and hints.
  2. MessageBold caption (12px, --text-caption bold) in --msg-fg. One short sentence.
  3. SubjectThe control or row it describes. Its aria-describedby points at the message’s id.

Variants

The tone is a modifier. Every tone has its own icon, so the meaning never depends on colour alone.

Sizes

Inline messages have one size: a 12px bold caption with a 16px icon. They are never larger than the thing they describe.

States

The message has no interactive states; it follows the state of its subject. Focus is forced with data-state; invalid and disabled use the real attributes.

  • Checking: while availability loads, a small inline spinner with “Checking Abigail’s calendar…” takes the message’s place.
  • Result: the message swaps in place. The control turns invalid (aria-invalid="true") only for danger.
  • Disabled field: the message keeps its colour; it describes a fact, not the control.

Responsive behaviour

  • The message wraps under its icon’s line instead of truncating. The icon stays aligned with the first line (align-items: flex-start).
  • Under a field it takes the field’s width. Beside a button in a .cluster it wraps onto its own line on phones, still directly after the button in the DOM.
  • On a ticket it sits in the body column, so on phones it stays above the perforated stub.

Theming

One component token, --msg-fg, sets the text and icon colour. It defaults to --color-fg-muted (the hint) and each tone points it at a status foreground: --color-info-fg, --color-success-fg, --color-warning-fg, --color-danger-fg. These are the text-safe status colours, not the icon colours, because the message is text.

.inline-msg--success { --msg-fg: var(--color-success-fg); }

In the dark theme the status foregrounds lighten to stay above 4.5:1 on the charcoal surfaces. Messages don’t appear on the stage or on yellow; if one is needed there, put the field in a paper island (data-theme="light"), as the booking bar does.

Accessibility

Role and pattern

A plain <span> or <p> referenced by its subject’s aria-describedby, so it is read after the control’s label and value. No APG widget pattern applies. When the message changes while the booker is on the page (an availability check finishing), wrap it in a role="status" element that is already in the DOM so the new text is announced politely. Errors after submit are also linked from the form’s error summary (see Forms).

Keyboard

KeyAction
TabNot focusable. The message is read when its subject receives focus.

Focus

Never move focus to a message. On a failed submit, focus goes to the error summary or the first invalid field, which then reads its message.

Labelling

The icon is decorative; the words carry the meaning, so “Abigail is free Sat 14 Nov” does not need a “Success:” prefix. Don’t type symbols such as ✓ into the text: screen readers read them out (“check mark”). A field with both a help text and a message lists both ids in aria-describedby, message first.

Motion

None. The message swaps in place with no transition, so nothing slides under the booker’s pointer.

Touch

Not a target. Keep at least 4px (--space-1) between the control and its message, which .field provides, so a tap on the message never lands on the control.

Content

  • One sentence, ideally under 40 characters so it fits on one line under a stub field. Drop the full stop for fragments (“Abigail is free Sat 14 Nov”); keep it for full sentences.
  • Name the person and the date: “Abigail isn’t free Sat 21 Nov”, not “Date unavailable”.
  • Errors say how to fix it: “Pick another date.” “Enter your church’s name.” Never “Invalid input”.
  • Hints give advice, not instructions the label already gives. “Most churches book 4–6 weeks ahead”, not “Choose a date”.
  • Use the Zamaro date format (“Sat 14 Nov”) and times like “2:14 p.m.”.
